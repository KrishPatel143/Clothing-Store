1. PROJECT OVERVIEW
================================================================================

linencut & more is a full-stack clothing e-commerce platform. Shoppers can
browse products, add items to a cart, and place orders. The differentiating
feature is a camera-based BODY SCAN that runs entirely in the browser:

  - Measures the shopper using MediaPipe (pose + segmentation)
  - Estimates chest, waist, hip, shoulder (cm)
  - Classifies body type and skin tone
  - Recommends correctly sized, well-matched clothing
  - Optionally generates a virtual try-on preview via Google Gemini

Privacy principle: camera frames are NOT uploaded for sizing. Only derived
numeric measurements are sent to the API. A try-on photo is stored locally
(IndexedDB) and sent to the server only when the user requests a preview;
the server does not persist that image.

7. AUTHENTICATION & AUTHORIZATION
================================================================================

  - Passwords hashed with bcrypt (salt rounds = 10)
  - On login/register, server issues a JWT containing { id, role }
  - Default expiry: 7 days (JWT_EXPIRES_IN)
  - Client sends: Authorization: Bearer <token>
  - requireAuth  → valid JWT + existing user
  - requireAdmin → user.role === 'admin'
  - Roles: 'customer' | 'admin'

Frontend guards:
  RequireAuth  → redirects to /login
  RequireAdmin → redirects to /login if not admin

9. BODY SCAN PIPELINE (CORE FEATURE)
================================================================================

UI FLOW (/scan)
  1. Intro: enter height (scale calibration), guidance, privacy note,
     optional manual measurement entry
  2. Full-screen camera with silhouette overlay
     Live framing feedback: "step back", "stand straight", "hold still"
     Auto-capture after ~1.5 seconds of good framing
  3. On-device processing (see below)
  4. Results: measurement cards, body type + tone notes,
     recommended products carousel with best-fit size pre-selected,
     option to save to profile

MEASUREMENT PIPELINE (client — measure.js + vision.js)
  a. MediaPipe Pose Landmarker → pixel / normalized skeleton
  b. User height (cm) → cm-per-pixel (and aspect-corrected X scale)
  c. MediaPipe Selfie Segmenter → torso silhouette
  d. Sample mask widths at chest / waist / hip vertical levels
  e. Ellipse / Ramanujan circumference from front width + depth ratios
       DEPTH_RATIO ≈ chest 0.72, waist 0.75, hip 0.78
  f. Landmark fallbacks if mask widths are missing/implausible
  g. Output: height, shoulder, chest, waist, hip (cm)

CLASSIFICATION (classify.js)
  Body type from chest/waist/hip ratios (style-guide thresholds)
  Skin tone: sample patch below nose → ITA (Individual Typology Angle)
             → Fair / Wheatish / Medium / Deep

PRIVACY
  Frames never sent for recommendations
  POST /api/recommendations receives only numbers + labels
  One scan frame may be saved in IndexedDB for try-on only

10. SIZE MATCHING & RECOMMENDATIONS
================================================================================

Shared logic:
  Server : server/src/utils/sizeMatcher.js
  Client : client/src/scan/fit.js  (instant "Fits me?" on product page)

ALGORITHM (weighted nearest-fit)
  Dimension weights:
    chest 0.35, waist 0.30, hip 0.20, shoulder 0.15
  For each size-chart row:
    Skip missing dimensions on either side
    deviation = garment - user (positive = roomier)
    If garment smaller (tight): multiply |diff| by TIGHT_PENALTY 1.6
    Weighted average deviation (cm)
  Best size = lowest deviation
  Fit confidence = 100 * exp(-deviation / 6)   # ~0cm → 100, ~10cm → ~20

PRODUCT RANKING (rankProducts)
  Start with fit confidence
  +12 if product suits body type (or product has no body-type filter)
  +8  if product suits skin tone (or no tone filter)
  Sort by matchScore descending

API: POST /api/recommendations
  Body: { measurements, bodyType, skinTone, category?, limit? }
  Filters products with stock > 0 and non-empty sizeChart
  Returns ranked list with recommendedSize, fitConfidence, matchScore
  Increments product.recommendedCount for analytics
  Public endpoint (guests can scan without login)

11. VIRTUAL TRY-ON
================================================================================

When:
  After a body scan, if a local photo exists in IndexedDB, product pages
  show "See how it looks on you".

Flow:
  Client sends personImageBase64 + productImageUrl → POST /api/tryon
  Server rate limit: 10 requests / minute / IP
  Server fetches product image, calls Gemini image generation
  Default model: gemini-2.5-flash-image (prompt-based; not a dedicated
  garment try-on model — results may vary)
  Returns JPEG preview; images are NOT stored on the server
  User can delete local photo from Profile

Setup:
  GEMINI_API_KEY in server/.env
  (https://aistudio.google.com/apikey)

Note: Works best with real JPEG/PNG product photos (not SVG placeholders).

13. KEY DESIGN DECISIONS (INTERVIEW TALKING POINTS)
================================================================================

1. Client-side computer vision
   Why: Privacy (no body video on server), lower bandwidth, faster feedback.
   Trade-off: Single RGB camera → circumference is an estimate (ellipse model),
   not a 3D body scan. UI labels results as estimates; manual size always allowed.

2. Height as scale reference
   Why: Without depth/LiDAR, absolute scale needs a known length. User height
   calibrates cm-per-pixel for the whole skeleton/silhouette.

3. Dual size matcher (client + server)
   Why: Instant UX on product pages without an API round-trip; server remains
   source of truth for recommendation lists and analytics.

4. Tightness penalty (1.6×)
   Why: A garment that is too small is worse than one that is slightly large;
   scoring reflects real shopping preference.

5. Try-on as optional Gemini proxy
   Why: Stateless server (no photo storage), rate-limited, feature-flagged by
   API key presence. Sizing still works without Gemini.

6. Guest-friendly cart + public recommendations
   Why: Lower friction — scan and browse before creating an account.

18. QUICK Q&A CHEAT SHEET
================================================================================

Q: What stack?
A: React + Vite + Tailwind, Node/Express 5, MongoDB/Mongoose, JWT, MediaPipe,
   Gemini for try-on.

Q: Where does CV run?
A: 100% in the browser (client-side MediaPipe).

Q: What is sent to the server for sizing?
A: Only derived measurements and labels — never scan video frames.

Q: How do you get cm without depth?
A: User height calibrates cm-per-pixel; silhouette widths + ellipse model
   estimate circumference.

Q: How is best size chosen?
A: Weighted distance across chest/waist/hip/shoulder; tightness penalized 1.6×;
   confidence via exponential decay of deviation.

Q: Auth model?
A: JWT Bearer tokens; bcrypt passwords; customer vs admin roles.

Q: Guest support?
A: Yes — cart locally; recommendations endpoint is public.

Q: Biggest challenge?
A: Reliable framing + converting 2D pixels into useful body measurements
   without a depth camera.
